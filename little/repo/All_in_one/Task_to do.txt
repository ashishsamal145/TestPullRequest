Task Breakdown & How to Achieve
1. Revenue Prediction Modelling file archive transfer

What: Move trained model outputs and artifacts from Azure Blob Storage → Oracle Object Storage (non-prod → dev/test, prod → UAT/prod).

How (based on your pipelines):

You already have:

Pipelines to read from Azure Blob (AZURE_STORAGE_WORKSPACE_CONTAINER, AZURE_MODEL2_OUTPUT_CONTAINER).

Pipelines/scripts to push to Oracle Object Store (similar to the file transfer YAML and sfdocmigration.ps1 you showed earlier).

Combine them:

Add a pipeline stage that downloads all required files from Azure Blob using Azure CLI (az storage blob download-batch).

Add a subsequent stage that uploads those same files to Oracle Object Storage using oci os object bulk-upload.

Parameterize the pipeline to support non-prod → dev/test and prod → UAT/prod.

This becomes your Archive Transfer Pipeline.

2. Kubernetes containers (training & scoring) → OKE

What: Migrate AKS jobs (multi-part ML training/scoring jobs) → Oracle Kubernetes Engine (OKE).

How:

Your current YAMLs (e.g., m3-training-pipeline-azure.yaml, consolidated_aks_scoring_deployment.yaml) deploy jobs to AKS.

To adapt:

Replace the Azure DevOps AKS service connections with OKE equivalents.

Replace Azure Blob mount references with OCI Object Storage mounts (via OCI FSS, S3-compatible SDK, or mount via CSI driver).

Reuse your job manifests (*-model-training-job.yaml, model-scoring-job.yaml) but update container image registry → push to Oracle Container Registry (OCIR) instead of Azure ACR.

End result: Training/scoring jobs run on OKE but produce artifacts into Oracle Object Storage.

3. SQL database migration (non-prod & prod)

What: Move Azure SQL DB (backup) → Oracle DB (non-prod + prod).

How:

Take BACPAC export of Azure SQL → convert to format suitable for Oracle.

Use Oracle GoldenGate, SQL Developer Migration Assistant, or Data Pump to import into Oracle.

Integrate pipeline:

A backup/export job from Azure SQL (scheduled or on-demand).

Transfer dump file to Oracle Object Storage.

Trigger Oracle import job (can be a DB system or Autonomous DB).

This ensures historical data continuity for training + scoring + reporting.

4. Web service (RPM) migration

What: Migrate existing Docker-based RPM web service (with Redis sidecar) → OKE.

How:

Take the current Docker image(s) → push to OCIR.

Write a Kubernetes Deployment + Service manifest for OKE with:

RPM web service container

Redis sidecar container

First step: Run against migrated historical Oracle DB (frozen data).

Second step: Modernize the container or rebuild it to read live Oracle data.

5. Azure Functions replacement (Excel & DB updates)

What: Azure Functions now move scoring outputs → SQL + generate Excel.
On Oracle, these won’t move, so you need final step in the scoring job.

How:

In the scoring job YAML, after scoring completes:

Add a step to push results directly into Oracle DB (using Python/SQL*Loader/ODI).

Add a step to generate Excel outputs (your dev.create-excel-files.sh & prod.create-excel-files.sh give a great blueprint).

Upload Excel files to Oracle Object Storage.

This avoids relying on Azure Functions.

Overall Flow Diagram (simplified)
Azure Blob (trained models) ----> [Pipeline] ----> Oracle Object Storage
Azure SQL DB -------------------> [Migration] ---> Oracle DB

AKS Jobs (train/score) ---------> [Adapt manifests + OCI mounts] ----> OKE Jobs
Docker Web Service (RPM + Redis) -> [Push to OCIR + Deploy] ----------> OKE Service

Excel Scripts (curl calls) -----> [Integrated in OKE jobs] -----------> Excel in OCI

End Goals

✅ All historical models & artifacts archived on Oracle Object Store.

✅ Training & Scoring jobs run natively on OKE + Oracle Object Store.

✅ Historical data migrated into Oracle DB.

✅ Web service runs on OKE instead of Azure.

✅ Excel/reporting steps embedded into Oracle pipelines.

✅ Azure infra can be retired → Oracle-only workloads.
